## 付费首跑失败与两处修复（2026-07-29）

首次付费 6 集运行 `43711ECB` **失败**：16/17 任务完成、5/5 审查完成、
0 待审批、133,408 / 180,000 token（未触顶），倒在 **t17 `package_artifact`**，
UI 显示 `fixed workflow failed: provider_or_task_failure`。

**根因无法判定，且证据已不可恢复**——这次失败暴露了两个结构性缺陷，已修：

### 修复 1：失败也落盘（`apps/desktop/src-tauri/`）

原落盘条件是 `status == "completed"`，**失败的运行什么都不留**。这次跑出的
16 个任务产物、5 份审查、13.3 万 token 的付费产出全部丢弃；磁盘上 4 个 run
目录清一色 `advisory`（成功），`43711ECB` 不存在，也无任何日志幸存。

新增 `status == "failed"` 分支写 `run-failure.json`（独立 schema
`story-run-failure/v1`、独立文件），含 error、已完成任务数、审查数、预算与
**完整事件流**。成功与失败**分文件分 schema**，`read`/`list`/`read_summary`
三个读路径不会开始看到半成品运行（有测试断言）。

> 这与 `ONLINE_POLICY_DESIGN` 已立的「不要丢弃 `t06` 淘汰候选」是同一条道理，
> 只是当初没有应用到失败的 run 上。

### 修复 2：失败码分类（`sidecar/campaign_adapter/workflow.py`）

原 `except Exception` 把所有非超时异常压成一个 `provider_or_task_failure`。现分四类：

| 失败码 | 含义 | 正确应对 |
|---|---|---|
| `final_review_rejected` | fail-closed 终审拒绝了包 | **改故事**，重试无用 |
| `artifact_validation_failed` | 包不满足产物契约（集数/schema） | 查生成或契约 |
| `capability_timeout` | 能力超时 | 重试 |
| `provider_or_task_failure` | 其余 | 查 provider |

第一类**根本不是故障，是闸门在正常工作**；旧标签会把操作者引去重试，而正确
动作是改故事。终态错误也从只有桶名改为带任务与细节：
`fixed workflow failed: final_review_rejected at t17: final review status='fail', critical findings=0`。
`record_failure` 只保留**第一个**失败——后续任务可能因前者连带失败，覆盖会把
根因替换成症状。

**测试抓到了不完整的修复**：`validate_package` 在 **t15 也调用**，最初只包了
t17，t15 的契约违规仍报成 provider 故障。已抽成 `_validate_package` 让两个调用
点分类一致。

新增测试 7 个（sidecar 5 / desktop 2）。当前计数：desktop 21 passed（原 19）、
sidecar 24 passed（原 19）、eval 75、root Rust 14 组，clippy `-D warnings`
root 与 desktop 均通过。

**重跑后如再失败**，`artifacts/advisory-runs/<run_id>/run-failure.json` 会留下
完整事件流与精确失败码，可直接区分「终审拒绝」与「包校验不过」——这两者是本次
唯一无法区分的两个竞争假设。
